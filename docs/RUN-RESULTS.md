# 运行结果与提示

运行列表、概览、详情和通知共用 `src/core/run-presentation.ts` 的说明逻辑。存储状态值与调度行为保持兼容，历史记录按已有证据生成说明，不重写运行结果。

## 状态

| 页面状态 | 内部值 | 含义及下一步 |
| --- | --- | --- |
| 已排期 | `scheduled` | 已安排但尚未开始 |
| 已排队 | `queued` | 等待队列处理 |
| 执行中 | `running` | 正在验证账号、检查状态和执行可用操作 |
| 执行成功 | `succeeded` | 任务正常完成，分项结果说明已确认的操作 |
| 检查完成 | `already_done` | 已检查且没有新增操作，说明今日已签到、暂无可领取权益或没有可兑换币券等原因 |
| 等待重试 | `waiting_retry` | 稍后自动重试或核实结果；新记录显示预计处理时间，维护暂停时顺延 |
| 需要核对 | `waiting_verification` | 最终结果不确定，先使用“只读核对”，仍不确定时由管理员核对平台记录并结案 |
| 执行失败 | `failed` | 没有确认全部完成，按分项原因处理；登录失效时重新扫码并恢复账号和任务 |
| 已取消 | `canceled` | 本次运行终止；旧记录没有具体原因时明确显示未记录，不编造原因 |

“检查完成”替代旧名称“无需执行”。它仍可能调用过平台接口，也可能发出了被平台判为重复的签到请求，不代表任务没有运行。

## 百度网盘判定

默认开启 PC 签到、App 签到和累计奖励：

1. 先只读验证平台账号身份，再进入任务。
2. PC 签到接口返回成功时记录签到结果；只有明确返回重复签到才记为“今日已签到”。
3. App 先查询今日状态，未签到时取得有效签到任务并提交，再查询确认结果。
4. 奖励只领取已达到累计天数且未全部领取的档位，领取前重查，领取后确认。
5. 每个操作前后查询成长值；查询不到时显示“未能确认”，不会当作 0。成长值增量为 0 本身不决定任务是否属于 `already_done`。

全部检查成功、报告中至少有一个操作步骤，且所有步骤均为 `already_signed` / `already_claimed` 时，适配器返回 `already_done`；否则正常完成返回 `succeeded`。仅启用奖励检查且没有生成操作步骤时，现有适配器仍返回 `succeeded`，页面根据证据说明“暂无可领取奖励”。本次没有改变这一历史判定。

关闭的功能显示“未启用”；缺少步骤时显示“未记录”或“等待检查”；请求失败或证据不足显示“结果未确认”。下一档奖励显示“还需签到多少天”，不承诺经过相同日历天数就会自动达标。

百度自动重试会保留已确认完成的步骤，对仍需处理的项目重查平台状态后继续；原有上限、维护开关与幂等约束不变。显式“只读核对”不会再次发送签到或领奖请求，详情优先展示新的核对结果。

## B 站判定

- `bili.vip_claim` 的 `not_available` 表示当前无可领取权益，不直接推断为“已经领取”或“会员资格不足”。
- `bili.exchange` 的 `no_coupons` 表示没有可兑换币券，本次未提交兑换请求。
- 只有余额变化确认的 `confirmed` 才说明领取或兑换已确认；未知结果显示等待核实或需要核对，不重复提交资产操作。
- 暂时续期不可用与登录硬失效分开说明；硬失效暂停账号及计划，提示重新扫码更新。

## 列表、详情与通知

列表展示任务中文名称、原因摘要和有证据的成长值/余额/奖励进度；详情展示每项结果、成长值前后变化与下一步操作。缺失或过旧的历史证据明确说明缺失，原始技术数据放在默认折叠的“诊断信息”中。

“正常完成次数”包含 `succeeded` 与 `already_done`，不等于新增领取次数。手动运行会立即入队，仍遵守配额、平台状态和防重复规则，不能强制再次获得当天奖励。

`already_done` 生成信息事件但不发送通知；`succeeded` 根据成功通知规则发送，失败/需核对根据异常通知规则发送。仅奖励检查等历史判定为 `succeeded` 的记录仍沿用成功通知策略。通知策略没有因显示名称变化而迁移或重置。
